Part A – Questions

2. Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?

A GitHub Actions workflow is a YAML file in the .github/workflows/ folder of the repository, so it is version-controlled together with the code. It has three levels: triggers, jobs and steps. The trigger (on:) says when the workflow starts, for example after a push or a pull request, on a schedule, or manually. A job is one unit of work which runs on its own virtual machine (runner). Jobs can run at the same time or one after another. Steps are commands or ready-made actions (e.g. actions/checkout) which run one after another in the job. If one fails, the next ones do not run.

My workflow starts after every push to the main branch, or manually with a button. It has one job, build-and-deploy, which runs on ubuntu-latest. A minimal pipeline for my app needs to check out the code, build an image, push it to a registry (Docker Hub) and deploy it to Rahti with the oc set image command. I also added oc rollout status, so the run turns red if the new pods do not start. Otherwise the green check would not prove anything. I tag the images with the short commit id (e.g. fcf2644), so I know exactly which code is running.

5. Explain the difference between a liveness probe and a readiness probe in Kubernetes/Rahti. What happens when each one fails?

Rahti does not guess if a container works, it checks it with probes. A liveness probe asks if the container is alive, so it means if it isn't stuck. If the liveness probe fails a few times in a row, Rahti restarts the container. A readiness probe asks if the pod is ready to take requests. If it fails, the pod is removed from the Service, but it is not restarted. So the main difference is that the liveness probe fixes the problem by restarting, and the readiness probe just moves the traffic away until the pod recovers.

In my backend, the liveness probe calls /healthz and the readiness probe calls /readyz. I scaled the backend to 2 pods and I created the file /tmp/not-ready in one of them, so /readyz returned error 503. After about 30 seconds, the pod was READY 0/1, but RESTARTS 0, and its IP disappeared from the endpoints. All requests went to the other pod, so a user would not notice anything. The pod came back by itself after I deleted the file. My /healthz does not fail when the database is down, because restarting the backend would not fix a database that is down.

6. What is alert fatigue, and how would you design a small set of alerts for a student project that avoids it?

An alert is a rule that watches metrics or logs and sends a message when a threshold is crossed. Alert fatigue happens when there are so many notifications that people start to ignore them, and then they miss the one important alert. It happens when the threshold is too strict, or when one random error starts the alert. The opposite problem is silent failure: there are no alerts, and you only find out about the outage from a user. A good rule is to alert only on things that a user would notice (the app does not work, requests fail, the database does not respond).

For my project I would have only two alerts. The first one: when more than 5% of the requests in 5 minutes have "level": "ERROR". One error is not enough, because it can happen by accident. The second one: when the backend has no ready pod for 2 minutes, because then nobody can use the app. I also avoided noise in the logs: probes are not logged (otherwise there would be hundreds of lines every hour), and a 404 has the level INFO, not ERROR, because it is the visitor's mistake, not the app's. So ERROR means that something is really broken on my side, and an alert on it makes sense.

7. Why should secrets (registry tokens, cluster login tokens) never be hard-coded into a CI/CD pipeline file? How does GitHub Actions handle this instead?

The pipeline file is in Git, so everyone who has access to the repository can see it. If the repository is public, the whole internet can see it. Git keeps the history, so even if you delete the password later, it stays in the old commits. Bots scan GitHub for leaked passwords. In the week 1 example, a developer got a bill of about $6,000 in one night after his keys leaked. Instead, GitHub Actions has repository secrets. The value is saved once in the repository settings and nobody can see it again. The workflow only uses the name of the secret, for example secrets.RAHTI_TOKEN. If the value is printed in a log by accident, GitHub replaces it with ***.

I saved three secrets: DOCKERHUB_TOKEN, RAHTI_TOKEN and RAHTI_SERVER. For Rahti I did not use my own token, but created a robot account, github-deployer, which has the edit role in only one project. The Docker Hub token can only read and push images, not delete them. So if a token leaked, an attacker could only do a little damage. I copied the robot token straight to my clipboard with pbcopy, so it was never shown on the screen or in a screenshot.

I used the same app as in week 4 and 5: an nginx frontend, a Flask backend and a MySQL database on Rahti. This week I added two things: a pipeline that deploys the app on every push, and health checks and logs so I can see if the app works.

1. The CI/CD pipeline

Before this week I deployed every change by hand. I built the image, pushed it to Docker Hub, ran oc set image and waited. Now GitHub Actions does the same steps on every push to main. It builds images for both the backend and the frontend, pushes them to Docker Hub and deploys them to Rahti. This page is part of the frontend, so the pipeline also deploys this page.

1.1 A robot account for GitHub

GitHub needs to log in to Rahti. My own login token stops working after a few hours, so I made a separate account for GitHub. In Rahti this is called a ServiceAccount. I named it github-deployer. It has a token that does not expire, and it only has the edit role in my project. If someone stole the token, they could only change this one project, not my whole CSC account. 

oc create serviceaccount github-deployer
oc policy add-role-to-user edit -z github-deployer
# then a Secret of type kubernetes.io/service-account-token holds its token

1.2 Secrets

The workflow file is public, so it cannot contain any password. I saved three values as GitHub repository secrets. The workflow only uses their names, like secrets.RAHTI_TOKEN. If a secret is printed in a log by mistake, GitHub shows *** instead.

3. Health checks

Rahti does not guess if my backend works. It asks the backend with two probes:

Probe Question Address What happens if it fails
Liveness "Are you alive?" /healthz Rahti restarts the container.
Readiness "Can you take visitors now?" /readyz Rahti takes the pod out of the Service, but does not restart it.

3.1 The two new addresses in the backend

/healthz always answers "alive". It also tells if the database is up or down, but it never fails because of the database. If the database is down, restarting the backend would not fix it, so the liveness probe should not depend on it.

/readyz answers 503 (not ready) in two cases: when the database does not answer, or when the file /tmp/not-ready exists in the pod. I added that file as a switch, so I can break the readiness check on purpose.

These addresses are not public. nginx only forwards /api/... to the backend. So I tested them from inside the pod with oc exec:

3.2 Probe configuration

The backend already had probes from week 4, but both asked /api/health, which always says "ok". I changed them with oc set probe. The same settings are now in k8s/04-backend.yaml: 

          # Readiness: "can I take traffic?" Fails -> pod leaves the Service.
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          # Liveness: "is the process alive?" Fails -> container is restarted.
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3

Example with the readiness probe: Rahti waits 5 seconds after the pod starts, then asks every 10 seconds. If there is no answer in 3 seconds, it counts as a fail. After 3 fails in a row the pod is taken out. So a broken pod leaves the Service after about 3 × 10 = 30 seconds, and one random slow answer does not do anything.

3.3 Breaking the readiness check on purpose

With only one backend pod, a failing readiness check would leave no pod in the Service and the whole app would stop. To show what readiness is for, I scaled the backend to 2 pods first. Both pods were in the Service endpoints (two IP addresses):

Then I turned on the switch in one pod, waited about 40 seconds, and checked again: 

oc exec backend-578bb6cddc-hpzv8 -- touch /tmp/not-ready

After that I removed the switch again and checked once more:

oc exec backend-578bb6cddc-hpzv8 -- rm /tmp/not-ready

So yes, the pod dropped out of the Service endpoints. It was not restarted, it just stopped getting traffic. The other pod answered all requests, so a visitor would not notice anything. When the pod was healthy again, it came back by itself. This is the difference between readiness and liveness: readiness only moves traffic away, liveness would restart the container.

After the test I scaled the backend back to 1 pod, because my project has a small CPU quota.

4. Logs and an alert rule

The backend now writes one line for every request. The line is in JSON, so a program can read it, not only a person. It has the time, the pod, the method, the path, the status code and how long the request took.

I do not log the probe addresses /healthz and /readyz. Rahti calls them every 10–20 seconds, so they would fill the log with hundreds of useless lines and hide the real requests.

I sent a few requests (one of them to a page that does not exist) and read the logs of both pods: 

oc logs -l app=backend --prefix --tail=8

One line from the log:

{"ts": "2026-10-02T07:12:36Z", "level": "INFO", "pod": "backend-578bb6cddc-hpzv8", "method": "GET", "path": "/api/weather", "status": 200, "duration_ms": 237.6}

What I can see in the logs:

  • /api/weather took 237.6 ms, the other requests took 0.1–50 ms. The weather request is the slowest, because it calls the Open-Meteo API.
  • /api/nope got status 404. Its level is still INFO, because 404 means the visitor asked for a wrong page, not that my app is broken. Only status 500 or higher gets the level ERROR.

4.1 A real alert rule

An alert should tell me when a user would notice a problem. If I send an alert for everything, I will start to ignore them. So I would keep only two rules:

  • Errors: if more than 5% of the requests in 5 minutes have "level": "ERROR", send me a message. One error is not enough, because one random fail can happen.
  • App down: if the backend has no ready pod for 2 minutes, send me a message. Then nobody can use the app.

With only oc logs I can count the errors myself, for example: 

oc logs -l app=backend --since=5m | grep -c '"level": "ERROR"'

5. Problems and solutions

a) Problem: My own Rahti token stops working after a few hours, so the pipeline would fail the next day.
Solution: I made the github-deployer account with a token that does not expire and only the edit role.

b) Problem: The teacher's example uses the GitHub registry (ghcr.io). Images there are private by default, so Rahti could not download them without another password.
Solution: I kept using Docker Hub, where my images are public, like in week 4 and 5.

c) Problem: I wanted to show the running version with APP_VERSION, but it always said 1.0.1, because the ConfigMap overwrites it.
Solution: I added a new value, GIT_SHA. The pipeline puts the commit id into the image, and /api/health shows it.

d) Problem: I could not use oc apply for the new probes. The YAML file still had the old image tag, so it would go back to old code, and the old code does not have /readyz.
Solution: First the pipeline deployed the new code, then I changed only the probes with oc set probe. The order matters. The YAML file now has a comment that the pipeline changes the image tag.

e) Problem: With one backend pod, a failing readiness check would stop the whole app, and the test would not show much.
Solution: I scaled to 2 pods for the test and back to 1 pod after it.

f) Problem: Gunicorn's own access log also wrote every request, including the probes, so every request was in the log twice.
Solution: I turned off the Gunicorn access log and kept only my JSON log, without the probe addresses.

g) Problem: The line Booting worker with pid: 4 in the log is not JSON. It comes from Gunicorn, not from my app.
Solution: Not fixed. A tool that reads the logs has to skip lines that are not JSON.

h) Problem: oc get endpoints printed a warning that Endpoints is deprecated.
Solution: It still works. Newer Kubernetes uses EndpointSlice instead. It does not change the result.

i) Problem: After the readiness fix, requests did not go to the two pods one after another. Sometimes the same pod answered 4 times in a row.
Solution: This is normal. The Service picks a pod at random, not in turns.
