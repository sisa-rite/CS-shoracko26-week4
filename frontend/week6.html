Part B – Automate and observe the app

I used the same app as in week 4 and 5: an nginx frontend, a Flask backend and a MySQL database on Rahti. This week I added two things: a pipeline that deploys the app on every push, and health checks and logs so I can see if the app works.

1. The CI/CD pipeline

Before this week I deployed every change by hand. I built the image, pushed it to Docker Hub, ran oc set image and waited. Now GitHub Actions does the same steps on every push to main. It builds images for both the backend and the frontend, pushes them to Docker Hub and deploys them to Rahti. This page is part of the frontend, so the pipeline also deploys this page.

1.1 A robot account for GitHub

GitHub needs to log in to Rahti. My own login token stops working after a few hours, so I made a separate account for GitHub. In Rahti this is called a ServiceAccount. I named it github-deployer. It has a token that does not expire, and it only has the edit role in my project. If someone stole the token, they could only change this one project, not my whole CSC account. 

oc create serviceaccount github-deployer
oc policy add-role-to-user edit -z github-deployer
# then a Secret of type kubernetes.io/service-account-token holds its token

1.2 Secrets

The workflow file is public, so it cannot contain any password. I saved three values as GitHub repository secrets. The workflow only uses their names, like secrets.RAHTI_TOKEN. If a secret is printed in a log by mistake, GitHub shows *** instead.

Secret What it is
DOCKERHUB_TOKEN a Docker Hub token that can read and push images, but cannot delete them
RAHTI_TOKEN the token of the github-deployer account
RAHTI_SERVER the address of Rahti

I copied the Rahti token straight to the clipboard with pbcopy, so it never showed on my screen or in a screenshot.

1.3 The workflow file

File: .github/workflows/deploy.yml

name: Build and deploy to Rahti

# When does the robot start? On every push to main,
# or by hand from the Actions tab ("Run workflow").
on:
  push:
    branches: [main]
  workflow_dispatch:

env:
  BACKEND_IMAGE: docker.io/shoracko26/lemp-backend
  FRONTEND_IMAGE: docker.io/shoracko26/lemp-frontend
  NAMESPACE: cs-rahti-project

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v4

      - name: Short commit id (used as the image tag)
        run: echo "TAG=${GITHUB_SHA::7}" >> "$GITHUB_ENV"

      - name: Log in to Docker Hub
        uses: docker/login-action@v3
        with:
          username: shoracko26
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Build and push backend (linux/amd64)
        uses: docker/build-push-action@v6
        with:
          context: .
          file: backend/Dockerfile
          platforms: linux/amd64
          push: true
          build-args: GIT_SHA=${{ env.TAG }}
          tags: ${{ env.BACKEND_IMAGE }}:${{ env.TAG }}

      - name: Build and push frontend (linux/amd64)
        uses: docker/build-push-action@v6
        with:
          context: .
          file: frontend/Dockerfile
          platforms: linux/amd64
          push: true
          tags: ${{ env.FRONTEND_IMAGE }}:${{ env.TAG }}

      - name: Install the oc client
        run: |
          curl -sSL https://mirror.openshift.com/pub/openshift-v4/clients/ocp/stable/openshift-client-linux.tar.gz | tar -xz oc
          sudo mv oc /usr/local/bin/oc
          oc version --client

      - name: Log in to Rahti
        run: oc login --token="${{ secrets.RAHTI_TOKEN }}" --server="${{ secrets.RAHTI_SERVER }}"

      - name: Deploy the new images
        run: |
          oc -n "$NAMESPACE" set image deployment/backend backend="$BACKEND_IMAGE:$TAG"
          oc -n "$NAMESPACE" set image deployment/frontend frontend="$FRONTEND_IMAGE:$TAG"

      - name: Wait until the new pods are running
        run: |
          oc -n "$NAMESPACE" rollout status deployment/backend --timeout=180s
          oc -n "$NAMESPACE" rollout status deployment/frontend --timeout=180s

      - name: Show what is running now
        run: |
          oc -n "$NAMESPACE" get deployment backend frontend -o wide
          oc -n "$NAMESPACE" get pods

1.4 What each part does

Part What it does
on: The trigger. The workflow starts on every push to main, or when I press "Run workflow".
jobs: One job called build-and-deploy. It runs on a new Ubuntu virtual machine that GitHub deletes after the run.
steps: The steps of the job. They run one after another. If one fails, the next ones do not run.
Short commit id Takes the first 7 characters of the commit id, for example fcf2644. This is the image tag. I do not use latest, because then I could not tell which commit is running.
Build and push The same as my old docker build and docker push, for linux/amd64. The commit id is also saved inside the backend image as GIT_SHA.
Install the oc client The GitHub machine does not have oc, so the workflow downloads it.
Log in to Rahti Logs in as github-deployer with the token from the secrets.
Deploy the new images Runs oc set image for the backend and the frontend.
Wait until the new pods are running Runs oc rollout status. If the new pods do not start in 3 minutes, the run turns red. So a green run means the app really runs on Rahti.
Show what is running now Prints the deployments and pods, so the run log also shows what was deployed.

3. Health checks

Rahti does not guess if my backend works. It asks the backend with two probes:

Probe Question Address What happens if it fails
Liveness "Are you alive?" /healthz Rahti restarts the container.
Readiness "Can you take visitors now?" /readyz Rahti takes the pod out of the Service, but does not restart it.

3.1 The two new addresses in the backend

/healthz always answers "alive". It also tells if the database is up or down, but it never fails because of the database. If the database is down, restarting the backend would not fix it, so the liveness probe should not depend on it.

/readyz answers 503 (not ready) in two cases: when the database does not answer, or when the file /tmp/not-ready exists in the pod. I added that file as a switch, so I can break the readiness check on purpose.

These addresses are not public. nginx only forwards /api/... to the backend. So I tested them from inside the pod with oc exec:

3.2 Probe configuration

The backend already had probes from week 4, but both asked /api/health, which always says "ok". I changed them with oc set probe. The same settings are now in k8s/04-backend.yaml: 

          # Readiness: "can I take traffic?" Fails -> pod leaves the Service.
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8000
            initialDelaySeconds: 5
            periodSeconds: 10
            timeoutSeconds: 3
            failureThreshold: 3
          # Liveness: "is the process alive?" Fails -> container is restarted.
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8000
            initialDelaySeconds: 15
            periodSeconds: 20
            timeoutSeconds: 3
            failureThreshold: 3

Example with the readiness probe: Rahti waits 5 seconds after the pod starts, then asks every 10 seconds. If there is no answer in 3 seconds, it counts as a fail. After 3 fails in a row the pod is taken out. So a broken pod leaves the Service after about 3 × 10 = 30 seconds, and one random slow answer does not do anything.

3.3 Breaking the readiness check on purpose

With only one backend pod, a failing readiness check would leave no pod in the Service and the whole app would stop. To show what readiness is for, I scaled the backend to 2 pods first. Both pods were in the Service endpoints (two IP addresses):

Then I turned on the switch in one pod, waited about 40 seconds, and checked again: 

oc exec backend-578bb6cddc-hpzv8 -- touch /tmp/not-ready

After that I removed the switch again and checked once more:

oc exec backend-578bb6cddc-hpzv8 -- rm /tmp/not-ready
Switch on Switch off again
Pod hpzv8 READY 0/1, still Running, RESTARTS 0 READY 1/1, RESTARTS 0
Service endpoints only 10.131.14.253:8000 10.129.22.156:8000 and 10.131.14.253:8000
Event Readiness probe failed: HTTP probe failed with statuscode: 503 no new fails
Who answered my requests always jz2v6 both pods

So yes, the pod dropped out of the Service endpoints. It was not restarted, it just stopped getting traffic. The other pod answered all requests, so a visitor would not notice anything. When the pod was healthy again, it came back by itself. This is the difference between readiness and liveness: readiness only moves traffic away, liveness would restart the container.

After the test I scaled the backend back to 1 pod, because my project has a small CPU quota.

4. Logs and an alert rule

The backend now writes one line for every request. The line is in JSON, so a program can read it, not only a person. It has the time, the pod, the method, the path, the status code and how long the request took.

I do not log the probe addresses /healthz and /readyz. Rahti calls them every 10–20 seconds, so they would fill the log with hundreds of useless lines and hide the real requests.

I sent a few requests (one of them to a page that does not exist) and read the logs of both pods: 

oc logs -l app=backend --prefix --tail=8

One line from the log:

{"ts": "2026-10-02T07:12:36Z", "level": "INFO", "pod": "backend-578bb6cddc-hpzv8", "method": "GET", "path": "/api/weather", "status": 200, "duration_ms": 237.6}

What I can see in the logs:

  • /api/weather took 237.6 ms, the other requests took 0.1–50 ms. The weather request is the slowest, because it calls the Open-Meteo API.
  • /api/nope got status 404. Its level is still INFO, because 404 means the visitor asked for a wrong page, not that my app is broken. Only status 500 or higher gets the level ERROR.

4.1 A real alert rule

An alert should tell me when a user would notice a problem. If I send an alert for everything, I will start to ignore them. So I would keep only two rules:

  • Errors: if more than 5% of the requests in 5 minutes have "level": "ERROR", send me a message. One error is not enough, because one random fail can happen.
  • App down: if the backend has no ready pod for 2 minutes, send me a message. Then nobody can use the app.

With only oc logs I can count the errors myself, for example: 

oc logs -l app=backend --since=5m | grep -c '"level": "ERROR"'

A real setup would collect the logs in a tool like Grafana or Prometheus and check the rule automatically every minute.

5. Problems and solutions

Problem Solution
My own Rahti token stops working after a few hours, so the pipeline would fail the next day. I made the github-deployer account with a token that does not expire and only the edit role.
The teacher's example uses the GitHub registry (ghcr.io). Images there are private by default, so Rahti could not download them without another password. I kept using Docker Hub, where my images are public, like in week 4 and 5.
I wanted to show the running version with APP_VERSION, but it always said 1.0.1, because the ConfigMap overwrites it. I added a new value, GIT_SHA. The pipeline puts the commit id into the image, and /api/health shows it.
I could not use oc apply for the new probes. The YAML file still had the old image tag, so it would go back to old code, and the old code does not have /readyz. First the pipeline deployed the new code, then I changed only the probes with oc set probe. The order matters. The YAML file now has a comment that the pipeline changes the image tag.
With one backend pod, a failing readiness check would stop the whole app, and the test would not show much. I scaled to 2 pods for the test and back to 1 pod after it.
Gunicorn's own access log also wrote every request, including the probes, so every request was in the log twice. I turned off the Gunicorn access log and kept only my JSON log, without the probe addresses.
The line Booting worker with pid: 4 in the log is not JSON. It comes from Gunicorn, not from my app. Not fixed. A tool that reads the logs has to skip lines that are not JSON.
oc get endpoints printed a warning that Endpoints is deprecated. It still works. Newer Kubernetes uses EndpointSlice instead. It does not change the result.
After the readiness fix, requests did not go to the two pods one after another. Sometimes the same pod answered 4 times in a row. This is normal. The Service picks a pod at random, not in turns.
