Part A – Questions

1. What is Infrastructure as Code, and which problems of manually created infrastructure does it solve? Use your own Week 1 VM setup as an example.

Infrastructure as Code (IaC) means that I describe servers, networks and firewalls in code files. I do not click them in a web console. The files are in Git, so I can see every change. A tool like OpenTofu reads the code. It calls the cloud API and builds what the code says. This solves many problems of manual work. With manual work, nobody remembers the settings. Rebuilding takes a long time, and the result is a little different. With IaC, the same code gives the same result every time. I can also delete everything with one command, so nothing runs and costs money by mistake.

I built my Week 1 VM by hand. It took about 4 hours. Today I cannot even see which image I used, because cPouta shows "-". The VM also has SSH open to the whole internet (0.0.0.0/0), and some extra ports from testing. Nobody wrote this down. This week the same kind of server is in code. I can see the image, the size and the firewall in the files. SSH is open only from my IP. After tofu destroy I built it again in 20.7 seconds, exactly the same.

5. What is configuration drift, how does it happen, and how does an IaC tool detect it?

Configuration drift means that the real infrastructure is different from the code. It usually happens when someone changes something by hand in the web console. For example, they "quickly fix" a firewall rule. OpenTofu has a state file. In the state file it remembers the ID of every resource it created. Before every plan, it asks the cloud about these IDs ("Refreshing state"). Then it compares the real values with the code. If something is different, the plan shows how to change it back.

I tested this in two ways. First, I deleted the HTTP rule by hand. My page stopped working. tofu plan noticed it and planned to create the rule again, and tofu apply fixed it. Second, I added a new rule for port 8080 by hand. This time tofu plan said "No changes". OpenTofu did not see the rule, because its ID was not in the state. This is dangerous. Port 8080 was open to the whole internet, and the tool said everything was fine. So the rule is: if something is managed by code, change it only in the code.

6. Explain the difference between provisioning and configuration management. Where do cloud-init and Ansible fit in?

Provisioning answers the question: which things exist? For example a VM, a firewall, a network port or a public IP. OpenTofu and Terraform are provisioning tools. Configuration management answers a different question: what is installed and running inside the VM? For example packages, files and services. cloud-init and Ansible are configuration tools. cloud-init runs only once, at the first boot of a new VM. Ansible connects over SSH to a running VM, and it can change the configuration at any time.

In my project, OpenTofu did the provisioning. It created the VM, the security group, the port and the floating IP. cloud-init did the configuration. It installed Apache and wrote my page. I saw the difference in my HTTPS test. I opened port 443 in the firewall with OpenTofu. But the page did not work over HTTPS, because Apache had no SSL and no certificate. Opening the port was provisioning. Setting up HTTPS in Apache would be configuration, so it would need cloud-init or Ansible.

8. Some changes in a tofu plan are made in place, while others require the resource to be destroyed and re-created. Why does this matter, and what kinds of changes would you be especially careful with?

An in-place change updates the resource that already runs. A replacement deletes the resource and creates a new one. This matters because a replacement can cause downtime. It can also delete data, because the new resource starts empty. The plan shows this before anything happens. It uses ~ for in-place and -/+ for replace, and it writes "forces replacement" next to the reason. So it is important to read the plan before typing "yes".

I saw both cases. When I changed the page text, the plan said the VM must be replaced. The reason was user_data, because cloud-init runs only at the first boot. The old VM was deleted and a new one was created, and the page was down for about 20 seconds. When I added the HTTPS rule, only one new rule was created. The VM was not touched and there was no downtime. I would be very careful with changes that replace a VM with important data, like a database server. I would also be careful with changes to the image, the SSH key or user_data, because they all replace the VM.

3. What each block in main.tf does and how they refer to each other

Block What it is Refers to
data …network_v2.project only reads my existing project network (made by CSC). It creates nothing. var.project_network
…keypair_v2.web uploads my public SSH key as week7-key var.ssh_public_key_path
…secgroup_v2.web the firewall week7-web-sg var.name_prefix
…secgroup_rule_v2.ssh port 22, only from my IP the security group, var.ssh_allowed_cidr
…secgroup_rule_v2.http port 80 from everywhere the security group
…port_v2.web the VM's network "socket" in the project network, protected by the security group the network (data), the security group
…instance_v2.web the VM itself; gets cloud-init.yaml as user_data the key pair, the port, image/flavor variables
…floatingip_v2.web the public IP from the public pool the port (not the VM)

I never write an ID in the code. For example the SSH rule says security_group_id = openstack_networking_secgroup_v2.web.id. The ID does not exist yet when I write the code. OpenTofu sees the reference, so it knows the security group must be created first. All references together make a dependency graph: 

security group  ←  rules (ssh, http, https)
security group  ←  port  ←  VM
                   port  ←  floating IP
key pair        ←  VM

4. variables.tf

variable "name_prefix" {
  description = "Prefix for the names of all resources, e.g. week7"
  type        = string
  default     = "week7"
}

variable "ssh_public_key_path" {
  description = "SSH public key path"
  type        = string
  default     = "~/.ssh/week7_ed25519.pub"
}

variable "image_name" {
  description = "Linux image for the VM, exactly as in Compute -> Images"
  type        = string
  default     = "Ubuntu-24.04"
}

variable "flavor_name" {
  description = "Name of flavor"
  type        = string
  default     = "standard.tiny"
}

variable "page_message" {
  description = "Page message"
  type        = string
  default     = "Shoracko26 - week 7 assignment page message - built with tofu"
}

variable "project_network" {
  description = "Name of the project network in cPouta (Network -> Networks)"
  type        = string
}

variable "ssh_allowed_cidr" {
  description = "Who may connect with SSH. Only your own IP, e.g. 203.0.113.45/32"
  type        = string

  validation {
    condition     = can(cidrhost(var.ssh_allowed_cidr, 0))
    error_message = "ssh_allowed_cidr must be in CIDR format, e.g. 203.0.113.45/32."
  }

  validation {
    condition     = var.ssh_allowed_cidr != "0.0.0.0/0"
    error_message = "SSH must not be open to the whole internet (0.0.0.0/0). Use your own IP, e.g. 203.0.113.45/32."
  }
}

variable "student_name" {
  description = "Student name"
  type        = string
}

Why project_network, ssh_allowed_cidr and student_name have no default: these values are different for every student, so a default would be wrong for everybody else. Without a default, the variable is required: if it is missing from terraform.tfvars, tofu plan stops and asks for it. This is most important for ssh_allowed_cidr. A default like 0.0.0.0/0 would quietly open SSH to the whole internet. At first I wrote default = "", but an empty default still makes the variable optional, so I removed it.

Validation: the first rule checks that the value is in CIDR format (for example 87.100.212.51 without /32 is stopped). I added a second rule that blocks 0.0.0.0/0. My week 1 VM had exactly this setting: SSH was open to the whole internet (see the last screenshot on this page).

5. cloud-init.yaml

#cloud-config

packages:
  - apache2

write_files:
  - path: /var/www/html/index.html
    defer: true # write AFTER packages are installed
    permissions: "0644"
    content: |
      <!doctype html>
      <html lang="en">
        <head>
          <meta charset="utf-8">
          <title>Week 7 - OpenTofu</title>
        </head>
        <body>
          <h1>Hello from ${student_name}!</h1>
          <p>${page_message}</p>
        </body>
      </html>

runcmd:
  - systemctl enable --now apache2

The first line #cloud-config is required, otherwise cloud-init ignores the file. packages installs Apache, write_files writes my page and runcmd starts Apache now and after every reboot. Normally cloud-init writes files before it installs packages, so Apache could overwrite my page with its default page. defer: true writes my file at the end, after the packages. ${student_name} and ${page_message} are filled in by OpenTofu with templatefile() in main.tf before the file is sent to the VM.

8. Experiment 1 – Change

Option A – change the page text

Prediction: the VM is updated in place, because OpenTofu is declarative. The public IP stays the same.

I changed page_message in terraform.tfvars and ran tofu plan.

Result: my first prediction was wrong – the VM was replaced. My second prediction was right – the IP did not change.

Explanation: the page text is part of user_data (the filled-in cloud-init.yaml), and the plan marks user_data with # forces replacement. cloud-init runs only at the first boot. The running VM already had its first boot, so a new user_data would never be used. The only way to get the new text is a new VM. "Declarative" means I describe the end result and OpenTofu decides how to get there – sometimes the only way is to replace the resource. The good thing is that the plan tells me before it happens. There was a short outage of about 20 seconds.

The IP stayed the same because the floating IP is attached to the port (port_id = openstack_networking_port_v2.web.id), not to the VM. The plan replaced only the VM, so the port and the floating IP did not change, and the new VM was plugged into the same port.

Option B – allow HTTPS too

Prediction: 1 to add, 0 to change, 0 to destroy. The VM will not be replaced. The page will work over https://.

I added a new rule to main.tf, a copy of the HTTP rule with port 443: 

resource "openstack_networking_secgroup_rule_v2" "https" {
  security_group_id = openstack_networking_secgroup_v2.web.id
  direction         = "ingress"
  ethertype         = "IPv4"
  protocol          = "tcp"
  port_range_min    = 443
  port_range_max    = 443
  remote_ip_prefix  = "0.0.0.0/0"
}

Result: the plan was exactly as predicted, but HTTPS does not work.

Explanation: compared to option A, this change does not touch the VM. The new rule refers only to the security group. The security group and the port do not change, so the VM at the end of the chain has no reason to change either, and there is no outage. A firewall rule can be changed on a running system, user_data cannot.

HTTPS does not work because the firewall is only the gate. Apache listens only on port 80, and nothing listens on port 443. The error is "connection refused": my request got through the firewall to the VM, and the VM said no. For HTTPS, Apache would need the SSL module and a certificate (for example from Let's Encrypt, which needs a domain name). That is configuration inside the VM (cloud-init), not provisioning (OpenTofu).

9. Experiment 2 – Drift

Part 1 – a deleted rule

Prediction: tofu plan will notice that the rule is missing and warn me.

In the web interface I deleted the HTTP (port 80) rule from week7-web-sg. The page stopped loading:

Result: OpenTofu noticed the missing rule. It did more than warn – it planned to create the rule again.

Part 2 – an added rule

Prediction: OpenTofu may notice the new rule, but an extra rule should not bother it, so it will not try to delete it.

In the web interface I added a rule for TCP port 8080 from 0.0.0.0/0 to the same security group:

Result: OpenTofu did not notice the new rule at all. After the test I deleted the manual rule.

Explanation: OpenTofu only checks the resources that are in its state file. In the "Refreshing state…" lines it asks cPouta about each ID it knows. In part 1 it asked about the HTTP rule's ID, cPouta said it does not exist, and the code says it should exist, so it planned to create it. In part 2 the new rule has an ID that OpenTofu never saw, so it never asks about it. It is invisible – the same as my week 1 VM.

This is dangerous: port 8080 was open to the whole internet, it was not in the code, and the plan said everything was fine. That is why, once something is managed with IaC, changes should be made only through the code.

10. Experiment 3 – Destroy and re-create

Prediction: all 8 resources (including the HTTPS rule) will be destroyed, but not the project network. They will disappear in the order they are written in the file (I was not sure). The IP will be the same after the rebuild.

Result: 8 destroyed and the network stayed – correct. The order was not the order in the file:

Wave Destroyed Why now
1 (at the same time) ssh, http and https rules, floating IP, VM nothing else refers to them
2 key pair, port they waited until the VM and the floating IP were gone
3 (last) security group the rules and the port referred to it

Explanation: the order comes from the references between the blocks, not from the file. In main.tf the security group is the second block, but it was destroyed last. When creating, the things that others depend on come first; when destroying it is exactly the other way round. Things that do not depend on each other are destroyed in parallel, which is why it was so fast. The project network survived because it is only a data block: OpenTofu did not create it, so it does not destroy it.

IP address: the IP is again 128.214.255.106, so my prediction was right, but partly by luck. The floating IP has a new ID (63596e86… before, 4e856b0d… after). It is a new floating IP that got the same address back from the public pool, because nobody else took it in the meantime. With the web_url output a changing IP does not matter much, because OpenTofu prints the new URL after every apply. If the address had to stay the same (for example for a domain name), I would create the floating IP outside this code and only read it with a data block, like the project network, or use a DNS name.

For me the biggest difference was not speed but knowing exactly what exists. Code makes sense for anything I will build more than once, share with other people, or need to rebuild after a failure. The drift experiment also showed the limit: IaC only works if everybody makes changes through the code.
